# לוח שנה — מערכת הזמנת משבצות פרסום

מערכת הזמנות אינטראקטיבית לפרסום בלוח שנה מודפס: המפרסם רואה מוקאפ של
העמוד, מרחף על משבצת כדי לראות מידות ומחיר, מאשר תנאים, בוחר עיר לפי
זמינות מלאי אמיתית, מעלה קובץ מוכן לדפוס ומשלם בסליקה חיצונית.

---

## הפעלה מקומית

### 1. מסד נתונים

הפרויקט דורש PostgreSQL. שתי דרכים:

**עם Docker** — מרים Postgres ו-MinIO בלבד:

```bash
docker compose up -d postgres minio minio-init
```

**בלי Docker** — השתמשו ב-PostgreSQL מנוהל (Neon, Supabase, Railway)
והדביקו את מחרוזת החיבור ל-`DATABASE_URL` בקובץ `.env`.
לאחסון הקבצים אפשר Cloudflare R2 — הוא תואם S3 והגדרות
`S3_*` עובדות מולו ללא שינוי.

### 2. סביבה

`​.env` כבר קיים עם סודות אקראיים שנוצרו מקומית. ודאו ש-`DATABASE_URL`
מצביע על המסד שלכם, ושנו את `SEED_ADMIN_PASSWORD`.

### 3. הקמה

```bash
npm install
npm run db:push      # יוצר את כל הטבלאות
npm run db:seed      # 14 משבצות, 12 ערים, תוכן, משתמש ניהול
npm run dev
```

- האתר: <http://localhost:3000>
- לוח הניהול: <http://localhost:3000/admin>
  (האימייל והסיסמה מתוך `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`)

## מודל הנתונים — הדבר החשוב להבין

### מלאי לפי עיר

לכל **עיר** מהדורת דפוס נפרדת, ולכן מלאי משבצות משלה. משבצת `LU-SQ-01`
נמכרת פעם אחת בירושלים ופעם אחת בבני ברק — אלה שני פריטים שונים.

### `SlotReservation` — הטבלה שמונעת מכירה כפולה

```
@@unique([cityId, slotId])
```

זו ההגנה האמיתית. גם אם שני לקוחות לוחצים "אישור" באותה מילישנייה,
המסד יפיל את השני ב-P2002 והמערכת תחזיר לו "המשבצת נתפסה". בדיקת
`count() < capacity` לבדה לא מספיקה — היא נתונה למרוץ.

רשומת תפיסה עם `expiresAt`:

- **תאריך** = החזקה זמנית. משתחררת אוטומטית אחרי `SLOT_HOLD_MINUTES`
  (ברירת מחדל 45 דקות) אם הלקוח נטש לפני תשלום.
- **null** = תפוסה לצמיתות. נקבע רק כשהתשלום אושר.

השחרור עצל: `releaseExpiredHolds()` רץ לפני כל בדיקת זמינות ולפני כל
ניסיון תפיסה. אין צורך ב-cron.

### כסף

מחירים נשמרים ב**אגורות** כמספר שלם (`priceAgorot`). מחיר ההזמנה
מוקפא ברגע היצירה — שינוי מחירון בלוח הניהול לא משנה הזמנות קיימות.

## תשלומים

### הזרימה

1. ללקוח נוצרת הזמנה, והמשבצת נתפסת בהחזקה זמנית.
2. הלקוח מעלה קובץ.
3. `POST /api/orders/:id/checkout` בונה קישור מה-`checkoutUrl` של ה-SKU,
   מוסיף `ref` / `amount` / `redirect`, ומעביר את ההזמנה ל-`AWAITING_PAYMENT`.
4. ספק הסליקה שולח **webhook** ל-`POST /api/payments/webhook`.
5. רק ה-webhook מסמן `PAID` והופך את התפיסה לקבועה.

> **חזרת הדפדפן מהסליקה אינה מסמנת "שולם".** היא רק מציגה ללקוח את
> עמוד הסטטוס. הלקוח שולט ב-URL שאליו הוא חוזר — לסמוך עליו זו
> פרצת גבייה.

### חתימת ה-webhook

הגוף הגולמי נחתם ב-HMAC-SHA256 עם `PAYMENT_WEBHOOK_SECRET`, והחתימה
מגיעה בכותרת `x-signature`. ההשוואה עמידה בפני התקפות תזמון.

מבנה האירוע הצפוי:

```json
{
  "eventId": "evt_123",
  "reference": "LU-7QK4X2",
  "status": "paid",
  "amount": 450.00,
  "paymentRef": "txn_abc"
}
```

אידמפוטנטי: `@@unique([provider, eventId])` — אירוע כפול נדחה בשקט.
כמו כן נבדקת התאמה בין הסכום ששולם למחיר ההזמנה.

### התאמה לספק אחר

אם מבנה ה-webhook של הספק שונה, נקודת ההתאמה היחידה היא
`eventSchema` ב-[src/app/api/payments/webhook/route.ts](src/app/api/payments/webhook/route.ts).
`markOrderPaid()` נשארת כמו שהיא.

### סליקת הדגמה

ל-SKU בלי `checkoutUrl` מוגדר, המערכת מפנה ל-`/checkout/demo` —
עמוד שמדמה אישור תשלום, כדי שאפשר יהיה לבדוק את התהליך מקצה לקצה
לפני חיבור ספק אמיתי. ברגע שמוגדר קישור אמיתי, מסלול ההדגמה מסרב
לטפל בהזמנה.

## אבטחה

| נושא | מימוש |
|------|-------|
| סיסמאות | scrypt (`N=16384`) מ-`node:crypto`, ללא תלות חיצונית |
| הגנה מפני מנייה | זמן תגובה אחיד גם כשהמשתמש לא קיים |
| הגבלת קצב | התחברות, יצירת הזמנה, העלאה — בזיכרון התהליך |
| קבצי אמנות | דלי פרטי; הורדה רק דרך presigned URL ל-5 דקות, אחרי אימות מנהל |
| בדיקת קבצים | חתימת בתים אמיתית, לא רק סיומת ו-MIME מהדפדפן |
| טוקן לקוח | טוקן יכולת אקראי 32 בתים; השוואה ב-`timingSafeEqual` |
| הרשאות | כל מסלול `/api/admin/*` בודק סשן בשרת |

> **הגבלת הקצב היא בזיכרון התהליך.** היא מספיקה למופע יחיד, שזו
> הפריסה כאן. אם תרחיבו ליותר ממופע אחד — להעביר ל-Redis, אחרת כל
> מופע סופר בנפרד.

## פריסה ל-VPS

### 1. קובץ סביבה בשרת

```bash
cp .env.example .env
```

ומלאו: `POSTGRES_PASSWORD`, `AUTH_SECRET`, `AUTH_URL`,
`S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `PAYMENT_WEBHOOK_SECRET`,
`NEXT_PUBLIC_BASE_URL`.

ייצור סודות:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

### 2. הרמה

```bash
docker compose up -d --build
docker compose exec app npx prisma db push
docker compose exec app npx tsx prisma/seed.ts
```

### 3. Nginx

העתיקו את [nginx/luach.conf](nginx/luach.conf), החליפו את שם הדומיין
ואת נתיבי התעודה.

> `client_max_body_size` חייב להיות **גדול** מ-`MAX_UPLOAD_MB`.
> אחרת Nginx חוסם קבצים גדולים לפני שהם מגיעים לאפליקציה, והלקוח
> מקבל שגיאה מבלבלת.

האפליקציה מאזינה על `127.0.0.1:3000` בלבד ואינה חשופה ישירות.

### מיגרציות

הפרויקט משתמש ב-`db push` להקמה מהירה. לפני עלייה לאוויר עם נתונים
אמיתיים, צרו מיגרציה ראשונה מול מסד נתונים חי:

```bash
npm run db:migrate -- --name init
```

ומאותו רגע בפריסות: `npm run db:deploy`.

## לוח הניהול

- **הזמנות** — סינון לפי סטטוס, חיפוש, פתיחת שורה לפרטים מלאים,
  הורדת קובץ האמנות, שינוי סטטוס ידני (מסונכרן עם תפיסת המשבצת).
- **ערים** — הוספה, עריכת קיבולת, מד תפוסה, הסתרה ידנית או
  אוטומטית כשהמלאי נגמר. מחיקה נחסמת לעיר עם היסטוריית הזמנות.
- **משבצות** — מחיר, שם, תגית, תיאור, והדבקת קישור הסליקה לכל מק״ט.
- **תוכן** — כל טקסט באתר, סעיפי התנאים, וכיבוי/הפעלה של עמוד הנחיתה.
